### 2026-11-17｜教学模型重新选型（覆盖上一条的 qwen2.5:7b 结论）

- 触发：距上次选型已过半月，且实测复核心存后才确认原方案存在偏差。
- 硬件复核：RTX 5060 Laptop，总显存 8151 MiB；**空闲仅 6223 MiB**（桌面已占 1588 MiB）。
  上一条"8GB 可全 GPU 运行 7B"的判断忽略了系统占用，这是本次改选的主因。
- 候选与淘汰理由：
  - `qwen2.5:7b`（~4.7GB）— 淘汰。上一代模型，同尺寸已有更新替代；且原判断未扣除桌面占用。
  - `qwen2.5-coder-7b`（已装）— 淘汰。实测 `tool_calls` 恒为 null，调用写在 content 里。
  - `qwen3.5:27b/35b`（17–22GB）— 淘汰，远超显存。
  - `qwen3.5:9b`（6.6GB）— 不作主力。权重已超 6223 MiB 空闲显存，必然部分层落 CPU，
    每一步工具循环都要等数秒，教学节奏会被拖垮；留作后续"对照模型"。
  - `qwen3:8b`（~5GB）— 淘汰。老一代；且 GitHub issue 19524 记录其在 Ollama 0.40.x 上
    因工具名不匹配丢弃调用，需 `OLLAMA_GO_TEMPLATE=false` 规避，教学场景不该先修兼容性。
- 决策：教学主力用 **`qwen3.5:4b`**（3.3–4.0GB）。全量进显存，还能留 2GB+ 给 KV cache，
  可把 `num_ctx` 从默认 4k 抬到 32k 以上——这比模型榜单排名更影响 agent 阶段成败。
- 关键参数发现：`langchain-ollama` 1.1.0 的 `ChatOllama` 支持 `reasoning`（关思考模式）
  与 `num_ctx`（手动抬上下文），恰好对应教学需要的"看清每一步"与"上下文足够"。
- 产出：`examples/00_probe_model.py` —— 三用例探针（工具调用 / 结果回填 / 结构化输出），
  argv 传模型名，逐项打印 PASS/FAIL 与 tok/s，可直接横向对比 4b 与 9b。
- 未解决问题：`qwen3.5:4b` 尚未拉取；探针未跑，能力仍属"网页标注"而非实测。
- 当前停留题目：暂无

### 2026-11-17｜模型就位与三项能力实测

- 环境结果：`qwen3.5:4b` 已拉取，3.32 GB，Ollama 标注 capabilities = `completion / vision / tools / thinking`。
- 探针结果（`examples/00_probe_model.py`，参数 `temperature=0, reasoning=False, num_ctx=8192`）：
  - 用例 1 单工具调用 PASS：`tool_calls` 非空，`get_weather(city="北京")`，`content` 为空（说明走的是原生通道，不是把 JSON 写正文）。
  - 用例 2 结果回填 PASS：追加 `ToolMessage` 后回答"北京现在天气晴朗，气温18°C，伴有2级西北风"，确实读了工具结果。
  - 用例 3 结构化输出 PASS：正确填出 `WeatherReport(city='上海', condition='多云', temperature_c=22)`。
- 性能实测：生成速度 76.4 / 77.7 tok/s，首次调用含加载 5.2s，后续 0.3–0.6s。
  该速度说明 4b 完全驻留显存，无 CPU 溢出——选型时的显存推算得到验证。
- 顺带修掉探针自身一个缺陷：用例 1 的判定 `ok = (... and args.get("city"))` 让 `ok` 变成了字符串 `"北京"`
  而非布尔值，靠 truthiness 侥幸判对，汇总行因此打印成"工具调用 北京"。已用 `bool(...)` 包裹。
- 结论：教学主力模型确定可用，`qwen2.5-coder-7b` 退为写代码用途，不再参与 Agent 教学。

### 2026-11-17｜第 2 课实证：抽掉 ToolMessage 会怎样

- 用 `examples/02_history_matters.py` 做对照实验：同一句"这两个城市哪个温度高"，A 组喂 9 条完整历史，B 组只留 3 条用户提问。
- A 组结果：`上海的 22°C 比北京的 18°C 要高`，准确复述两个数字，无冗余。
- B 组结果：**没有编造温度**。它声称无法获取实时天气，输出约 300 字气候常识（夏季副高、冬季寒流），最后建议用户自己去搜天气应用。
- **修正此前预判**：我原判"缺 tool 消息会让模型编造温度"，实测不成立。4b 在缺数据时倾向用泛泛而谈填充，而不是硬编数字。
- 这比编造更隐蔽：B 组回答篇幅是 A 组的十倍、看起来更"专业"，但一个有效信息都没有，
  且完全丧失"前两轮已经查过"这一事实，等同于退回第一次对话。
- 教学点：历史缺失的后果不只是"说错"，更是"答非所问且不自知"。产品里这类回答最难被用户识破，
  也解释了为什么 RAG 必须显式实现"找不到就说不知道"，而不能指望模型自觉。
