# LangChain / LangGraph 弹性学习方案

> 版本基线：2026-11（Python 3.12、langchain 1.4.x、langgraph 1.2.x）
> 组织方式：任务粒度 + 里程碑。不按"第几周"排期，只按"能不能过关"推进。

## 0. 结论先行：原路径是否合理

`LangChain 基础 → LangGraph 基础 → RAG → 单 Agent → 多 Agent` 的主干成立，但按 1.0 之后的框架现状，建议做两处调整：

| # | 调整 | 原因 |
|---|---|---|
| 1 | RAG 提前到单 Agent 之前 | RAG 只依赖"模型 + 检索"，不依赖图编排；它还是后面研究型 Agent 的第一个工具，先做可以让单 Agent 阶段有真实可调的东西 |
| 2 | "LangGraph 基础"移到单 Agent 之后 | 1.0 之后单 Agent 的标准入口 `create_agent` 直接构建在 LangGraph 上。先当使用者跑通 Agent，再拆开看"图"，节点/边/状态才有具体指代物 |

调整后的路径：**LangChain 基础 → RAG → 单 Agent → LangGraph 图原语 → 多 Agent**。

递进关系一句话：**会调模型 → 会给模型知识 → 会让模型自己决定用哪个工具 → 能精确控制这个循环 → 能组织多个循环协作**。每一层解决上一层"失控"的地方：RAG 解决模型不知道，Agent 解决流程写死，LangGraph 解决 Agent 不可控/不可恢复，多 Agent 解决单个 Agent 职责过载。

## 1. 学习阶段与定位

| 阶段 | 核心目标 | 关键概念 | 最终产出物 |
|---|---|---|---|
| 0 准备 | 能稳定调用支持工具调用的模型，能看到 trace | 模型接入、.env、依赖锁定、LangSmith/Langfuse、代理与连通性 | 可复现的最小环境 + 一条 trace |
| 1 LangChain 基础 | 不靠 `create_agent`，用底层组件完成一次可控调用 | ChatModel、Messages、Prompt、Tool Schema、`bind_tools`、结构化输出、流式、Runnable | 多轮 CLI 小助手（工具 + 结构化输出 + 流式 + trace） |
| 2 RAG | 对自选文档集做出有评测数字的 RAG | 解析、切分、embedding、向量库、检索、rerank、引用、评测 | 领域 RAG 助手 + 20 题评测报告 |
| 3 单 Agent | 用 `create_agent` 构建可观测、有限额、可审批的研究型 Agent | agent loop、工具协议、middleware、interrupt、预算与终止、评估 | 研究型 Agent（RAG 工具 + 审批 + 评测） |
| 4 LangGraph 图原语 | 能亲手画出 `create_agent` 的等价图，并实现持久化与恢复 | StateGraph、reducer、条件边、checkpointer、interrupt/resume、流式、子图、并行 | 手写 ReAct 图 + 带审批的工单流 |
| 5 多 Agent | 理解三种协作形态，并能量化说明"何时不该拆" | supervisor、handoff、subagents、map-reduce、共享/隔离状态、预算、失败传播 | 多 Agent 协作系统 + 单/多基线对比 |

阶段 0 可以并入阶段 1 的第一个整块任务，不必单独占一个阶段。

## 2. 推荐路径与过关关系

```
阶段 1 ──> 阶段 2 ──> 阶段 3 ──> 阶段 4 ──> 阶段 5
 组件直觉     检索能力     自主决策     编排可控     分工协作
   │            │            │            │            │
   └─ 每阶段出口：可运行产物 + 能解释 + 能定位一次失败 ─┘
```

- 阶段 2 的产出是阶段 3 的工具，阶段 3 的产出是阶段 4 的对照物（先会用，再拆开）。
- 阶段 4 不是"重学一遍"，而是回答"`create_agent` 到底替我做了什么"。
- 阶段 5 的前置条件是阶段 3/4 都有可运行的对照基线，否则无法判断多 Agent 是否值得。
- 允许回退：阶段 4 卡住时回到阶段 3 读一次 trace，通常比继续看文档有效。

## 3. 通用学习机制（针对时间碎片化）

### 3.1 两种粒度如何分工

| | 碎片时间（15–30 分钟） | 整块时间（2–4 小时） |
|---|---|---|
| 适合做什么 | 读一个概念、看一段官方示例、改一行跑一次、记录一条结论、看一条 trace | 环境与依赖、端到端跑通、调试状态图、评测与对比、重构 |
| 不适合做什么 | 装环境、跨文件调试、跑评测 | 从头读大段文档 |
| 结束条件 | 留下一条可提交的记录或一个 commit | 跑通一条完整链路，或定位一个具体问题 |

一条硬规则：**碎片任务必须"打开电脑就能开始"**。所以每次学习结束前，写下"下一步的第一个动作"（5 分钟内能开始的动作，例如"把 chunk_size 改成 500 跑一次"），下次不需要重新进入状态。

### 3.2 保持连贯性的五个机制

1. **任务栈**：每个阶段在仓库里维护一个 TODO 清单（本文件即可），碎片时间只从栈顶取任务。
2. **可提交物**：每个碎片时间至少留下一个 commit 或一段笔记，让进度可见、可回看。
3. **阶段看板**：未开始 / 进行中 / 待过关 / 已过关 四列，只移动卡片，不排日期。
4. **冷启动包**：每个整块任务提前写清启动命令（装什么、跑哪个文件、看哪个 trace），避免整块时间浪费在回忆上。
5. **每周 15 分钟对齐**：看里程碑差在哪，只调整任务优先级，不重排时间表。
6. **交接记录**：每次学习结束把新知识点、答题评价、理解偏差、未解决问题、当前停留题目和下一步计划追加到 `Doc/学习交接记录.md`，下次从记录恢复状态。

### 3.3 "过关"不等于"看完"

每阶段的过关条件是四件事同时成立：

- 产物能跑，别人按 README 能复现；
- 能用自己的话解释关键概念，不看文档；
- 能定位一次真实失败（哪一步、输入是什么、为什么错）；
- 能说出这一阶段哪些旧教程写法已经过时。

## 4. 各阶段详解

### 阶段 1｜LangChain 基础

**学习目标**：不依赖 `create_agent`，用底层组件完成一次可控调用——多轮消息、工具绑定、结构化输出、流式打印。

**重点概念**：ChatModel 接口；System/Human/AI/Tool 四类消息；提示模板；工具 Schema（类型注解 + docstring）；`bind_tools`；`with_structured_output`；流式；Runnable/LCEL（知道管道符即可，不重仓）；trace。

**碎片任务**
- 读 Messages 与 content blocks 官方文档
- 跑一次 `invoke`，打印 `AIMessage` 的全部字段
- 改 system prompt，对比输出差异
- 用 Pydantic 定义结构化输出并跑通
- 写一个函数工具，观察 `bind_tools` 生成的 schema
- 在 trace 里找到一次工具调用，读模型看到了什么
- 用 `stream` 逐块打印
- 读 Runnable 概念页，理解 `|` 只是组合

**整块任务**
- 环境、版本锁定、tracing（可与阶段 0 合并）
- 多轮 CLI 助手（含历史裁剪策略）
- 两个工具 + 参数校验 + 错误回传
- 结构化输出 + 流式
- 封装为可复用模块，写 README

**避坑提醒**

| 坑 | 识别信号 | 对策 |
|---|---|---|
| 照抄 2024–25 旧教程 | `from langchain.chains import ...`、`AgentExecutor`、`initialize_agent` | 这些已迁到 `langchain-classic`；以 `docs.langchain.com` 和 release notes 为准 |
| 把 LangChain 当"必须写 Chain" | 为了一个调用套三层链 | 1.x 的核心是可组合组件，链只是组合方式之一 |
| 工具描述含糊导致乱调 | 模型反复调错工具名/参数 | docstring 是写给模型看的说明书，写清何时用、参数含义 |
| 只跑不 trace | 出错时不知道模型看到了什么 | 每一次调用都留 trace，先看输入再看输出 |
| 不同模型能力差异 | 结构化输出时好时坏 | 阶段 0 先用 3 个最小用例验证目标模型的工具调用与结构化输出能力 |
| 同步/异步混用 | CLI 里 `invoke`、服务里 `ainvoke` 行为不一致 | 一个项目内统一风格 |

### 阶段 2｜RAG 专项

**学习目标**：对自选文档集做出端到端 RAG，并用评测数字而不是感觉来调参。

**重点概念**：文档解析与清洗；切分策略；embedding；向量库；检索（top-k、MMR、混合检索）；rerank；上下文组装与引用；评测（召回、忠实度、答案相关性）；query 改写；父子块/上下文增强。

**碎片任务**
- 读 document loaders / splitters 文档
- 用 3 组 chunk_size/overlap 各跑一次检索
- 比较两种 embedding 的维度与成本
- 读 retriever 接口，理解它只负责"给片段"
- 写 10 个"答案在原文中"的评测问题
- 分析一条 trace 的检索结果，人工判断命中与否
- 读 rerank 概念，理解它解决什么问题

**整块任务**
- 数据摄取管线（增量更新、去重、元数据）
- 两种检索策略对比（纯向量 / 混合 + rerank）
- 20 题评测集 + 指标脚本
- 引用展示与"找不到就说不知道"
- 失败归因报告（解析、切分、检索、生成各占多少）

**避坑提醒**
- 不建评测集就调参：只看一两个问题会被偶然结果误导。
- 把"检索到了"当"答对了"：检索命中不等于生成忠实。
- 忽略解析质量：PDF 表格、扫描件、页眉页脚会污染切分。
- chunk 一刀切：按标题/段落切通常优于固定长度。
- 评测题泄漏进知识库，指标虚高。
- 先辩论向量库选型：先跑通，再按数据量换。
- embedding 模型与查询语言/领域不匹配。

### 阶段 3｜单 Agent

**学习目标**：用 `create_agent` 构建一个可观测、有限额、可审批的研究型 Agent。

**重点概念**：agent loop（模型 → 工具 → 模型）；消息状态；工具调用协议；system prompt 设计；middleware（摘要、守卫、审批、日志）；interrupt；checkpoint 初识；预算与终止条件；评估。

**碎片任务**
- 读 `create_agent` API 与 middleware 文档
- 跑官方最小示例
- 把阶段 2 的 RAG 封装成工具接入
- 加步数/预算上限
- 写一个日志 middleware
- 试一次 interrupt 审批
- 读一条完整 trace 的循环过程
- 写 5 条评测用例

**整块任务**
- 研究型 Agent 端到端（检索 + 计算 + 写作）
- 危险工具前暂停审批（HITL）
- 上下文压缩 middleware
- 失败重试与超时
- 20 例评测 + 与无工具的基线对比

**避坑提醒**
- 无步数/预算上限：工具循环会把 token 烧光。
- 工具过多且描述重叠：模型选择困难，先控制在 3–5 个。
- 把安全边界交给 prompt：危险操作在代码层校验。
- 不保存 thread、不看 trace：失败无法复现。
- 一个 Agent 包打天下：先跑通，再按职责拆。
- 中间件堆料：每个 middleware 都要能说清它改变了哪一步。

### 阶段 4｜LangGraph 图原语

**学习目标**：手写 `create_agent` 的等价图；掌握状态、边、持久化、中断、流式、子图与并行。

**重点概念**：StateGraph；state schema 与 reducer；节点；普通边/条件边；`Command`；compile；checkpointer 与 `thread_id`；interrupt/resume；time travel；streaming modes；subgraph；`Send`（map-reduce）；durability。

**碎片任务**
- 读 StateGraph 概念页
- 手写两节点线性图
- 加一条条件边
- 加 reducer（消息追加 vs 覆盖）
- 读 checkpointer 与 thread 概念
- 跑一个 interrupt 示例
- 可视化图
- 读 streaming modes，各跑一次

**整块任务**
- 手写 ReAct 图，与 `create_agent` 行为对照
- 会话持久化 + 进程重启后恢复
- 审批工单流（interrupt → 修改状态 → resume）
- 子图拆分
- 时间旅行复现一次失败

**避坑提醒**
- 状态里放不可序列化对象：checkpoint 会失败。
- reducer 写错：消息重复或丢失，且往往难以发现。
- 路由函数里写业务逻辑：图变得不可读、不可测。
- 不设递归上限：条件边死循环。
- interrupt 后重新 `invoke` 而不是 resume：会从新状态开始。
- 子图状态隔离/共享混淆：先明确哪些键共享。
- 只会画图不理解"哪个节点写了哪个状态"。

### 阶段 5｜多 Agent

**学习目标**：理解 supervisor、handoff、并行/子代理三种形态；能用数据说明多 Agent 何时值得。

**重点概念**：supervisor/router；handoff；subagents；并行 map-reduce；共享状态 vs 隔离状态；deep agents（规划、虚拟文件系统、子代理）；全局预算与终止；失败传播；多 Agent 评估。

**碎片任务**
- 读多 Agent 概念页
- 画 supervisor 图
- 改一个 handoff 条件
- 写 critic 的评审提示
- 读 deepagents 概览
- 分析一条多 Agent trace 的交接点

**整块任务**
- 内容工厂：planner → 并行 researcher → writer → critic
- 全局预算与终止条件
- 与单 Agent 基线对比（质量、成本、延迟）
- 失败注入（某 Agent 超时）与降级

**避坑提醒**
- 为多而多：没有单 Agent 基线，就无法证明拆分有价值。
- 靠自然语言交接导致信息失真：交接内容结构化。
- 没有全局预算/终止：多个 Agent 互相等待或循环。
- 职责边界模糊：每个 Agent 的输入、输出、禁区要写清。
- 不可观测：每个子 Agent 的 trace 都要能单独看。
- 忽略同步与调用成本。

## 5. 里程碑检验标准

在满足"可运行 + 能解释 + 能定位失败 + 知道旧写法"的前提下，用下面这些具体动作自检：

| 里程碑 | 检验方式（不看教程完成） |
|---|---|
| M0 环境 | 30 分钟内从零跑通官方最小 Agent 示例，并在 trace 平台看到调用链；能说出目标模型是否支持 tool calling |
| M1 基础 | 写一个多轮 CLI：2 个工具 + 结构化输出 + 流式；能在 trace 中指出每一轮模型看到的完整输入 |
| M2 RAG | 一份新文档集，2 小时内从摄取到问答跑通；20 题评测有数字；能把 3 个错误样本归因到解析/切分/检索/生成 |
| M3 单 Agent | 演示研究型 Agent；演示一次中断审批；根据 trace 定位一次"该调工具没调"或"参数调错" |
| M4 图 | 白板画出图结构、reducer 与 checkpoint 位置；实现一次中断恢复；解释 `create_agent` 对应哪张图 |
| M5 多 Agent | 演示多 Agent 项目；给出与单 Agent 的质量/成本/延迟对比；说清每个 Agent 何时应该合并回去 |

## 6. 学完后的能力清单

- 能把一个需求映射到"组件 / 检索 / Agent / 图 / 多 Agent"中的正确层级；
- 能给出选型理由，而不是"因为教程这么做"；
- 能观测：trace、状态、评测集，能定位失败发生在哪一层；
- 能控制：预算、步数、权限、终止条件；
- 能交付：可复现环境、README、评测报告；
- 能自我更新：会读 release notes 和迁移指南，能识别过时教程。

## 7. 作品集建议

| 作品 | 展示点 |
|---|---|
| 领域 RAG 助手 | 用你已有领域资料（例如 AFSIM 文档）做语料；附评测集与失败归因报告，证明不是"demo 能答" |
| 研究型 Agent | 工具编排、审批、预算、trace；展示一次被拦截的危险操作 |
| 可恢复审批工作流 | LangGraph 持久化 + 中断恢复 + 时间旅行；展示进程重启后继续 |
| 多 Agent 协作系统 | planner/researcher/writer/critic；附单 Agent 基线对比与成本分析 |
| 复盘文章或评测小工具 | 把"踩坑 + 指标 + 版本迁移"沉淀成可复用内容 |

## 8. 资源与版本基线

- 官方文档以 `docs.langchain.com` 为准；LangGraph 概念页与 reference 同站，避免缓存旧域名页面。
- 版本基线（2026-10）：`langchain` 1.4.x、`langgraph` 1.2.x；单 Agent 入口是 `langchain.agents.create_agent`，`langgraph.prebuilt.create_react_agent` 已弃用；旧版 Chain/Agent 模式迁至 `langchain-classic`。
- 建议锁版本：`pip install "langchain[openai]==1.4.*" "langgraph==1.2.*" langsmith`，并提交 lock 文件。
- 观测：LangSmith（有免费额度）或自建 Langfuse；敏感数据先脱敏再上传。
- 教程识别信号：出现 `create_react_agent`、`AgentExecutor`、`langchain.chains`，基本可判定为 1.0 之前的写法。
- 每两周花 10 分钟看一次 release notes / migration guide，比追教程划算。
