# 模型下载：直连与国内镜像

> 结论先行：Ollama **没有** registry 镜像机制。所谓"换镜像加速"在这套工具链里不存在，
> 真正的国内方案只有一条——从魔搭（ModelScope）下 GGUF，再用 `ollama create` 导入。
> 但在本机实测下来，两个源速度几乎相同，先看第 1 节的数据再决定要不要折腾。

## 1. 先看清事实：瓶颈在哪

2026-11-17 本机实测，两个源各拉 25MB 片段：

| 源 | 地址 | 实测速度 | 3.32GB 预计耗时 |
|---|---|---|---|
| Ollama 官方 | `registry.ollama.ai` → Cloudflare R2（新加坡） | 1.71 MB/s | ≈ 32 分钟 |
| 魔搭 ModelScope | `modelscope.cn` | 1.85 MB/s | ≈ 30 分钟 |

两个独立源跑出同一量级的速度，说明**瓶颈在本地带宽或出口，不在源**。换源省不下时间。

另外要澄清两个常见误解：

- `OLLAMA_HOST` 是 **API 服务监听地址**，与模型下载源无关。网上"改 OLLAMA_HOST 加速下载"的说法是错的。
- Ollama 没有 `npm config registry` 那样的镜像配置项。任何号称"Ollama 官方镜像站"的第三方域名，
  都是自行反代的非官方服务，不建议用来下模型（文件完整性无从校验）。

## 2. 路径 A：直连拉取（推荐，最可靠）

```powershell
ollama pull qwen3.5:4b
```

- 拉取的是官方包，chat template 与 tool calling 配置都由官方保证，不会出现"导入了但不会调工具"的问题。
- **支持断点续传**：中断后重跑同一条命令，会从已下载的层继续，不会从头开始。
- 进度会显示类似 `pulling 2648d3... 42% ▕██████    ▏ 1.4 GB/3.3 GB  1.9 MB/s`。

拉取期间可以另开一个窗口确认进度：

```powershell
ollama list          # 完成后才出现在列表里
ollama ps            # 看是否有模型驻留显存
```

拉完立刻验证能力（不要跳过，官方标注 tools 不等于真能产出 tool_calls）：

```powershell
.\.venv\Scripts\python.exe examples\00_probe_model.py
```

## 3. 路径 B：魔搭下载 GGUF 再导入（只在直连不可用时用）

魔搭上 `Qwen/Qwen3.5-4B` 官方仓库**只有 9.3GB 的 BF16 原始权重，没有 GGUF**，Ollama 无法直接使用。
可用的 GGUF 在社区仓库 `unsloth/Qwen3.5-4B-GGUF`（已核实存在），共 24 个量化档，常用几个：

| 文件 | 大小 | 说明 |
|---|---|---|
| `Qwen3.5-4B-Q4_K_M.gguf` | 2.74 GB | 推荐档位，质量与体积平衡 |
| `Qwen3.5-4B-Q5_K_M.gguf` | 3.14 GB | 略好，显存仍充裕 |
| `Qwen3.5-4B-Q8_0.gguf` | 4.48 GB | 接近无损，留的 KV cache 空间变少 |
| `mmproj-F16.gguf` | 0.67 GB | 视觉投影层，只做文本任务可不带 |

步骤：

```powershell
# 1) 装下载工具
pip install modelscope

# 2) 只下需要的两个文件（不要整仓拉，会多下 20 多个量化档）
modelscope download --model unsloth/Qwen3.5-4B-GGUF --local_dir .\models\qwen35-4b `
  --include "Qwen3.5-4B-Q4_K_M.gguf" "mmproj-F16.gguf"

# 3) 在同目录写 Modelfile（文件名就是 Modelfile，无后缀）
#    内容：
#    FROM ./Qwen3.5-4B-Q4_K_M.gguf
#    FROM ./mmproj-F16.gguf

# 4) 注册进 Ollama
cd .\models\qwen35-4b
ollama create qwen3.5-4b-local -f Modelfile

# 5) 验证
ollama run qwen3.5-4b-local "你好"
```

### 这条路的风险，必须提前知道

手动导入时，Ollama 从 GGUF 元数据里读取 chat template。如果 template 与 Ollama 的
tool-call 解析器不匹配，模型就会把调用写成正文里的 JSON，`tool_calls` 恒为 null
——**这正是本项目在 `qwen2.5-coder-7b` 上踩过的坑**。

所以导入后**必须**跑探针验证；不通过就回到路径 A，不要在 Modelfile 里手写 TEMPLATE 硬凑：

```powershell
.\.venv\Scripts\python.exe examples\00_probe_model.py qwen3.5-4b-local
```

另一个差异：官方包自带视觉投影层，导入版默认是纯文本。阶段 1 用不到视觉，但不带
`mmproj-F16.gguf` 的话，阶段 2 处理 PDF 扫描件时就没有图像能力。

## 4. 如果拉取真的卡住

按可能性从高到低排查：

1. **代理干扰**。若系统开着代理，`ollama pull` 会继承系统代理设置。代理不稳时表现为
   长时间 0 字节或反复中断。可临时清空代理环境变量后重试（PowerShell）：
   ```powershell
   $env:HTTP_PROXY=""; $env:HTTPS_PROXY=""; $env:NO_PROXY="localhost,127.0.0.1"
   ```
2. **磁盘空间**。模型存在 `%USERPROFILE%\.ollama\models`，需要 3.4GB 以上余量。
   可用 `OLLAMA_MODELS` 指向 D 盘：设为系统环境变量后重启 Ollama 服务。
3. **服务未启动**。`ollama app.exe` 在托盘运行；若 `curl http://localhost:11434/api/version`
   无响应，手动启动 `ollama serve`。
4. **先下小档看速度**。用一个 1.5GB 的量化档试水（如 `qwen3.5:2b`），能下完说明链路没问题，
   只是 4b 文件大。

## 5. 本项目的取舍

选 **路径 A（直连）**，理由不是速度（两条路一样），而是**可验证性**：
官方包的 template 与 tool calling 由官方保证，出问题时能确定是代码问题而非模型装配问题。
教学场景最怕的就是"分不清是框架的错还是模型装配的错"。

只有在直连连续失败两次以上时，才切到路径 B，并且切过去之后第一件事是跑探针。
